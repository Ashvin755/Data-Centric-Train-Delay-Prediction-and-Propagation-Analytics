\begin{abstract}
Indian Railways delay analytics faces a critical data bottleneck: there is no widely available, open, station-level, machine-learning-ready dataset suitable for longitudinal modeling of delay propagation. This paper addresses that gap through a data-centric approach that prioritizes robust data engineering before advanced prediction. We designed and deployed an automated collection pipeline using GitHub Actions cron workflows, RailRadar application programming interface (API) polling, and Supabase PostgreSQL persistence. The system tracks journey lifecycle states and stores station-level scheduled and actual timestamps together with delay fields, using an idempotent, fault-aware architecture. From January to June 2026 the pipeline ran continuously for a fixed panel of ten trains, covering both single-day and multi-day services, and collected more than 61,000 unique station-level records. Exploratory analysis of the collected data showed that specific station segments persistently add delay while others persistently recover it; this behavior is quantified with a station-pair delay-delta indicator, \emph{alpha}, which classifies adjacent halt pairs into delay-adding, neutral, and delay-recovery zones. Baseline next-station delay prediction reaches 4.78 minutes mean absolute error with the best sequence model on held-out journeys, although current performance is not yet sufficient to capture all route-level patterns. The outcome of this phase is both a usable dataset-generation infrastructure and an analysis framework supporting delay-propagation modeling, ETA forecasting, and timetable-robustness analysis for Indian Railways.
\end{abstract}

\section{Introduction}
%=====================================================================

\subsection{Background and Need}
Indian Railways operates one of the largest rail networks in the world, carrying more than 8 billion passenger journeys annually over approximately 68{,}000~km of route \cite{indian_railways_stats}, and is correspondingly sensitive to delay propagation across stations and routes. A delay introduced on one segment is frequently carried forward, amplified, or partially absorbed as the service proceeds, affecting rolling-stock reuse, crew and platform scheduling, and downstream connectivity. Two services sharing the same corridor may therefore end with very different delay profiles, depending on the segments traversed and where recovery capacity exists along the route.

Despite this operational scale, no openly accessible, continuously updated, and methodologically reproducible station-level dataset exists for delay analytics. Existing studies are often constrained to coarse aggregated reports, manual surveys prone to sampling bias, or inaccessible proprietary sources. This matters directly for modeling, because delay-prediction quality depends heavily on consistent, long-duration data that preserves journey context. A model trained on a short snapshot, or on inconsistently ordered station records, cannot reliably separate persistent route-level effects from one-off operational disturbances.

This project therefore began with a data-centric goal: build a reliable automated collection pipeline first, and only then use the collected dataset for exploratory analytics and predictive modeling. Framing the problem this way also makes the resulting dataset reusable for research questions beyond the immediate forecasting objective, such as route-level diagnosis and segment benchmarking.

\subsection{Project Motivation}
Unlike European and Japanese systems with open operational feeds, the Indian context lacks station-level, lifecycle-complete delay traces. This motivated a reproducible collection pipeline with documented methodology, enabling delay prediction, schedule-reliability analysis, and network optimization. The first phase of this work was presented at Technovision 2026 at Samrat Ashok Technological Institute (SATI), Vidisha, and received the first prize in the Artificial Intelligence and Data Science (AI\&DS) domain.

\subsection{Objectives}
The key objectives of this work are:
\begin{enumerate}
    \item to build a scalable, automated, and reproducible pipeline that collects station-level delay data for selected trains;
    \item to maintain journey lifecycle tracking so that completion and failure context is preserved;
    \item to perform train-wise exploratory analysis that identifies persistent delay patterns;
    \item to quantify station-segment behavior using a robust route-level metric (alpha);
    \item to establish baseline delay-prediction models as a reference for future improvements;
    \item to document the collection methodology so that the dataset and results are reproducible and extensible.
\end{enumerate}

\subsection{Contributions in the Current Phase}
The main contributions of this phase are:
\begin{itemize}
    \item \textbf{Automated collection pipeline:} continuous operation since January 2026 with no manual intervention;
    \item \textbf{Station-level dataset:} more than 61{,}000 unique records collected from January to June 2026;
    \item \textbf{Exploratory data analysis (EDA) workflow:} train-wise, halt-station-aligned delay-trend plots for ten trains;
    \item \textbf{Station-pair alpha analysis:} identification of delay-add and delay-recovery zones along a route;
    \item \textbf{Modeling benchmarks:} random forest, polynomial regression, time-series trials (ARIMA, SARIMA, Prophet, Chronos), tuned gradient boosting (XGBoost), and sequence models (LSTM, TCN).
\end{itemize}

\section{Related Work}
\label{sec:related}
%=====================================================================

\subsection{Railway Delay Modeling in the International Context}
International railway systems such as those in the United Kingdom and Germany provide open operational feeds that support reproducible analytics \cite{uk_rail_data,german_rail_data}. Building on such feeds, prior studies have applied machine learning and delay-propagation models for delay forecasting and traffic optimization \cite{oneto2018train,flier2009delay,goverde2010railway}. These datasets typically include structured temporal events and multi-year coverage, which makes replication and comparison of published results feasible and allows models to be evaluated under controlled conditions.

\subsection{Indian Context and Data-Availability Gap}
For Indian Railways, meaningful research on delay prediction exists, but reproducible open-data access remains limited. Gaurav and Srivastava proposed a zero-shot Markov framework using data from 135 trains over March 2016 to February 2018, yet the underlying dataset and source were not openly released for direct reproduction \cite{gaurav2018zeroshot}. Arshad also reported machine-learning-based delay prediction with data references to online running-status sources, but without an openly shareable benchmark dataset accompanying the publication \cite{arshad2019prediction}. More recently, the RSTGCN study claimed a nationwide Indian railway delay dataset, but at the time of review that dataset was not publicly accessible through the links in the paper's repository trail, which limits independent verification and reuse \cite{chowdhury2025rstgcn}. While high-level operational reports do exist \cite{indian_railways_stats}, model-ready station-level traces with continuous open access are still uncommon.

\subsection{Requirements Implied by Prior Work}
Taken together, the studies above implicitly define the properties that a usable delay dataset must satisfy. First, records must be station-level rather than only train-level, because propagation is a segment-wise phenomenon. Second, each record must carry journey context, so that observations from different runs of the same service can be aligned and compared. Third, the station ordering must be stable across journey dates, otherwise segment-level comparisons are not meaningful. Fourth, the observation horizon must be long enough to separate persistent effects from transient ones. Finally, the collection process should be documented well enough to be reproducible, since otherwise reported accuracy figures cannot be independently validated.

\subsection{Comparative Insight and Research Gap}
Most prior work emphasizes prediction models; however, prediction quality is strongly data-dependent. In our case, delay forecasting was the intended primary objective, but the lack of consistently accessible dataset infrastructure became an enabling bottleneck that had to be solved first. The literature therefore indicates that data quality, consistency, and operational context are prerequisites for robust prediction. Accordingly, this phase prioritizes systematic data generation and station-level interpretability as a prerequisite stage, with forecasting-performance improvement as the downstream target. In particular, this work contributes a data-first collection and analysis pipeline for the Indian context and introduces an interpretable station-pair alpha indicator for operational insight prior to stronger model claims.

\section{Problem Statement}
\label{sec:problem}
%=====================================================================

\subsection{Core Problem}
The primary long-term problem is robust train delay forecasting for Indian Railways, especially station-to-station delay propagation and arrival-time reliability improvement. In practical execution, however, we encountered an enabling problem first: the absence of sufficiently open, continuously collected, station-level data needed to train and validate such models.

\subsection{Observed Challenges}
Several concrete challenges motivate this formulation:
\begin{itemize}
    \item open historical traces that preserve journey-state context are missing from available public sources;
    \item reproducible collection pipelines for Indian routes are rarely documented publicly;
    \item comparing station behavior across journey dates is difficult without a stable station ordering;
    \item baseline models struggle without route-aware feature design and normalized preprocessing;
    \item existing public-facing estimated-time-of-arrival systems are often perceived as heavily timetable- or heuristic-driven, which motivates a stronger data-driven alternative for delay-aware prediction.
\end{itemize}

Each of these challenges compounds the others. Without journey-state context, abandoned or incomplete runs cannot be excluded, which biases any downstream statistic. Without a stable station ordering, the same physical segment may appear at different positions on different days, making segment-level aggregation unreliable. And without normalized preprocessing, even a well-specified model tends to fit dominant, high-delay segments at the expense of the smaller recovery effects that are operationally informative.

\subsection{Formal Problem Statement}
The project problem is to design and operate an automated data pipeline that collects reliable station-level delay data for selected Indian trains, and then to develop a data analysis framework that can:
\begin{enumerate}
    \item reveal persistent station-segment delay behavior;
    \item quantify delay accumulation and delay-recovery zones; and
    \item provide benchmark delay-forecasting baselines for future model enhancement.
\end{enumerate}

\subsection{Relation to Existing Schemes}
Unlike approaches that begin directly with model training on limited snapshots, this work first constructs a reproducible data foundation with lifecycle tracking, idempotent storage, and explicit quality checks. This directly addresses the enabling bottleneck---data availability---so that the primary objective of better delay forecasting can subsequently be pursued with stronger evidence. The same design also makes the collection process auditable, because every stored record can be traced back to a specific journey date and polling cycle.

\section{Proposed Work: System Architecture and Methodology}
\label{sec:proposed}
%=====================================================================

\subsection{System Overview}
The implemented system uses a serverless execution model driven by scheduled workflows and cloud database storage. Two polling workflows are maintained: one for single-day trains and one for multi-day trains, reflecting their substantially different journey durations. Each workflow is triggered on a fixed cron schedule through GitHub Actions---every 5 h for single-day trains and every 12 h for multi-day trains---and executes a dedicated Python polling script that queries the RailRadar API \cite{railradar_about} and persists resulting records to a Supabase PostgreSQL database. Because scheduling is external to the application code, collection continues without manual intervention, and the same scripts can be redeployed locally for verification or backfill. Keeping the two service classes on separate schedules also ensures that long-distance services are not polled at a cadence designed for short commuter runs. Fig.~\ref{fig:arch} shows the overall collection architecture.

\subsection{Dual-Phase Polling Methodology}
Collection proceeds in two phases.

\subsubsection{Phase 1: New-Journey Detection}
For each configured train, the pipeline checks whether a journey record already exists for the current Indian Standard Time (IST) date. If not, RailRadar live data is queried to confirm the journey's start conditions. On a valid start, a new tracker row is inserted with initial flag values so that the journey becomes eligible for ongoing polling.

\subsubsection{Phase 2: Ongoing-Journey Tracking}
Every journey marked as neither completed nor abandoned is polled. Completion is detected when the current station code matches the configured destination code; on completion, the retrieved route station records are inserted into the main dataset table. On repeated polling failures, the flag counter increases and beyond a configured threshold eventually triggers abandonment of that journey, without writing station-level data. This separation ensures that incomplete or unreliable journeys never contaminate the analytical dataset, while still preserving the fact that the journey occurred. Fig.~\ref{fig:state_machine} shows the journey state machine used for this lifecycle tracking.

\subsection{Database Design}
The data model consists of three connected tables. The \texttt{train\_info} table stores static metadata for monitored trains, including train name, journey type (single-day or multi-day), destination station code, and journey duration. The \texttt{journey\_status\_flags} table tracks journey-level state---completion, abandonment, and the polling flag count---keyed by a unique combination of train number and journey date. The \texttt{rail\_data} table stores station-level observations with scheduled and actual arrival and departure timestamps and arrival and departure delay fields, keyed by train number, journey date, and station code, and additionally records the distance from origin in kilometers. \subsection{Reliability and Data Integrity}
Data reliability is maintained through four design decisions:
\begin{itemize}
    \item an idempotent insertion policy avoids duplicate station rows when the same journey is polled repeatedly;
    \item composite keys maintain journey isolation when multiple journeys are handled in parallel;
    \item API failures are handled through controlled flag increments rather than by corrupting existing state;
    \item completion detection and record insertion are logically tied together, so partially observed journeys cannot leave the dataset inconsistent.
\end{itemize}
Idempotency is the property that matters most in continuous polling, because a station's record may legitimately be observed several times before departure delay is finalized. By keying insertions on the journey and station identity, repeated observation refreshes the same row instead of appending duplicates, so record counts remain meaningful as a measure of collection volume.

\subsection{Delay Variables and Journey Representation}
Two primary variables are used throughout the analysis: delay at arrival and delay at departure, both measured in minutes. These are combined with the scheduled and actual timestamps at each station, which allows delay accumulation and recovery to be examined segment by segment rather than only as an end-to-end figure.

Journey lifecycle tracking is treated as a first-class part of the data model rather than as an afterthought. Instead of collecting raw snapshots alone, each journey carries explicit completion and abandonment flags, which enables controlled extraction of completed journeys and reduces duplication in downstream analysis. This is what allows the analysis to state coverage explicitly: a segment observed on 30 of 30 journey dates is quantitatively different from one observed on 4 of 30.

Route analysis is performed on the halt-only station order. Using a single static halt sequence for a train provides consistent sequence alignment across different journey dates, so that any two journeys of the same train can be compared position by position and segment-level differences can be attributed to operational behavior rather than to changing station lists.

\subsection{Data Processing and EDA Workflow}
After the collection pipeline was established, a structured analysis phase was executed in Python Jupyter notebooks, in the following order:
\begin{enumerate}
    \item initial statistical EDA and data-quality checks, including column profiling, datatype checks, missing-value ratios, and timestamp parse diagnostics;
    \item time normalization and event-time construction, converting Unix timestamps to IST and deriving a consistent journey date for sequence analysis;
    \item train-wise delay-curve visualization, plotting station against departure delay across journey windows using the static halt-station ordering;
    \item pattern discovery, identifying visually that some station segments repeatedly add delay while others repeatedly cover up delay;
    \item baseline modeling, providing first benchmark models for delay forecasting using classical machine learning and time-series baselines;
    \item segment-level experimentation on Train 18238, computing station-pair delay deltas and alpha values and producing top-10 rankings for delay-adding and delay-recovery pairs.
\end{enumerate}
Steps one and two are prerequisites rather than analysis: without consistent time normalization, the same physical event can be assigned to different journey dates, which silently corrupts every later comparison. Step three produces the visual evidence on which the alpha hypothesis rests, and steps five and six split the work into model-based and indicator-based tracks that can be evaluated independently.

\subsubsection{From Visualization to Alpha Experimentation}
The alpha methodology was derived directly from the observed shapes of the station-wise delay trends. In the notebook, the alpha experimentation section formalizes pairwise delay deltas, computes the median and mean alpha, and reports ranked outputs, including the top-10 delay-adding and top-10 recovery segments. Reporting both a ranked list and an explicit coverage ratio for every pair keeps the interpretation honest: a large alpha supported by only a few observations is visibly distinguished from one supported by the full analysis window.

\subsection{Station-Pair Alpha Metric}
To quantify station-segment behavior, alpha is defined on adjacent halt-station pairs within a journey as the difference between the departure delay recorded at the downstream station and the departure delay recorded at the upstream station:
\begin{equation}
\alpha_{(i \rightarrow i+1)} = d_{i+1}^{(dep)} - d_i^{(dep)}
\label{eq:alpha}
\end{equation}
where $d_i^{(dep)}$ denotes the departure delay in minutes at station $i$. A positive alpha indicates a delay-addition segment, a negative alpha indicates a delay-recovery (cover-up) segment, and a practical threshold of $|\alpha| \geq 1$ minute is applied to filter negligible fluctuations. Median alpha across the observed journey dates is used as the primary robust indicator, with mean alpha computed as a sensitivity check so that outlier journeys cannot silently dominate the ranking.

The construction deliberately measures the difference between two adjacent departure delays rather than an absolute delay value. This makes the indicator independent of how delayed a journey already was when it reached the upstream station, so a segment's tendency to add or absorb delay can be compared across journeys with very different starting conditions.

\subsection{Dataset Snapshot and Preprocessing}
The collection system ran from January to June 2026 and collected more than 61,000 unique station-level records. The data used for the visualizations and modeling in this paper spans 1 January to 24 May 2026. For analysis, timestamp fields were parsed and converted to IST, and both the journey date and the halt-station sequence were normalized to support cross-journey comparison. The primary fields used in this phase are train number, journey date, station code, scheduled and actual arrival and departure timestamps, arrival and departure delay, and the event-time-derived ordering used for sequence construction.

The dataset therefore contains, for each completed journey of each monitored train, an ordered sequence of halt stations with scheduled and actual times and the corresponding delay values. Because insertion is idempotent and completion is verified before insertion, the station-level record count is a usable measure of collection volume rather than an inflated count of repeated polling attempts.

Table~\ref{tab:dataset_stats} summarizes the dataset as evaluated for analysis quality. The departure-delay distribution is strongly right-skewed (median 26 minutes, mean 44 minutes, 95th percentile 141 minutes), which motivates the median-based aggregation used by the alpha metric and the choice of absolute over percentage-based model errors. About 10\% of records lack a realized departure time and about 4\% a realized arrival time at extraction; these rows are removed by listwise deletion in the modeling stages, and the distance-from-origin column is unpopulated throughout and therefore unused.

\subsection{Station-Pair Alpha Findings}
Applying the alpha metric of \eqref{eq:alpha} to Train 18238 over the 30-day window shows that the route does not follow a single monotonic trend; it alternates between delay-add and recovery zones. Representative delay-adding segments include MTJ~$\rightarrow$~RKM, BPHB~$\rightarrow$~R, and DHO~$\rightarrow$~MRA, while representative recovery segments include AGC~$\rightarrow$~DHO, KATL~$\rightarrow$~NGP, and DUA~$\rightarrow$~BINA. This supports the hypothesis that station and segment operational effects are persistent and measurable. Fig.~\ref{fig:alpha_profile_18238} shows the corresponding alpha profile for the route.

Two features of these rankings are operationally meaningful. First, the largest effects are concentrated at a small number of route positions rather than distributed evenly along the corridor, which suggests that improvement efforts would be more effective if targeted at specific segments than if applied uniformly. Second, additions and recoveries are interleaved along the route: a corridor that appears severely delayed overall may still contain segments that consistently absorb delay, and those segments are precisely where the route's existing slack is being consumed.

\subsection{Baseline Modeling and Evaluation}
Baseline next-station delay prediction was performed with a journey-wise split to reduce leakage between training and evaluation. Splitting by journey rather than by row ensures that observations from the same run do not appear on both sides of the split, which would otherwise inflate apparent accuracy because consecutive stations of one journey are strongly correlated; concretely, the latest 20\% of journey dates are held out as the test set. Initial supervised models (random forest \cite{breiman2001random} and polynomial regression) were fit on Train 11077 over the January--March extract of the collection, while the main modeling effort targeted Train 18238 over the analysis window of 1 January to 24 May 2026 and added statistical baselines, tuned gradient boosting, and sequence models. Table~\ref{tab:model_metrics} reports the resulting evaluation; the sequence models are scored over sliding windows of the same held-out journeys.

Even the best current results are not yet sufficient to capture all learned route-level patterns, which is consistent with the finding that delay behavior is strongly segment-dependent and therefore not fully described by the features used so far.

\subsubsection{Time-Series Trials}
ARIMA and SARIMA \cite{boxjenkins1976}, Prophet \cite{taylor2018forecasting}, and Chronos \cite{woo2024chronos} baselines were explored, but their initial outcomes were not adequate for the desired route-pattern capture. The current phase therefore treats these as reference baselines rather than final predictive claims, and they are retained to document which model families were assessed before the next phase of feature engineering. A plausible reason for their limited performance at this stage is that the series available per train and per station are still short, so classical time-series models have too little history to estimate stable seasonal components.

Consistent with RSTGCN's practice of treating zero actual delay explicitly when computing percentage error \cite{chowdhury2025rstgcn}, we also report MAPE with caution because near-zero delays make it unstable in our setting.

\subsection{Limitations in the Current Experimental Phase}
The present results are subject to the following limitations:
\begin{itemize}
    \item selection bias can occur when severely delayed journeys cross the abandonment thresholds and are therefore excluded from the completed-journey dataset;
    \item coverage is currently limited to about four and a half months of continuous data across ten trains (January--June 2026), so network-wide generalization is pending;
    \item exogenous-factor comparison is limited: this phase did not observe strong seasonal extremes such as severe fog or monsoon rain, so weather-impact learning is weak in the present baselines;
    \item experiments are primarily single-source and do not yet integrate richer factors such as weather feeds, infrastructure constraints, or control actions;
    \item baseline models do not yet fully encode station-network structure, so interactions between neighboring segments remain implicit.
\end{itemize}
The first two limitations interact: if severely delayed journeys are more likely to be abandoned, and abandonment is more likely during disruptive periods, then the retained dataset is progressively biased toward undisturbed operations. This is one reason the alpha results are presented as segment tendencies with explicit coverage rather than as unconditional delay estimates. Data collection was paused on 8 June 2026 following a change to the RailRadar API, so observations are not available after that date.

\section{Conclusion and Future Work}
\label{sec:conclusion}
%=====================================================================

\subsection{Conclusion}
This work established a data-centric pipeline for Indian Railways delay analytics and demonstrated that reliable station-level data generation is feasible with automated cloud workflows. It has produced:
\begin{itemize}
    \item a running collection infrastructure that requires no manual intervention;
    \item a real-time dataset of more than 61,000 station-level records collected January--June 2026;
    \item interpretable route-segment findings obtained through the alpha analysis; and
    \item reproducible baseline modeling benchmarks for next-station delay prediction.
\end{itemize}
The core academic contribution of this phase is not a final high-accuracy predictor, but a robust and transparent data foundation together with interpretable diagnostics that make future modeling meaningful in a domain where operational variability is high and open data are scarce. Because the pipeline and the analysis both operate on explicit, traceable records, subsequent modeling work can be compared on a common and reproducible basis. The alpha results in particular turn the dataset into an operational diagnostic: they identify which segments consistently consume recovery margin and which consistently provide it, information that is useful even before a predictive model is deployed.

The dataset collected in this phase is available on reasonable request through \url{https://forms.gle/5JM1UZqLPvYseyuUA}.

\subsection{Future Work}
Planned next steps are:
\begin{enumerate}
    \item advanced preprocessing and normalization of delay and time features;
    \item station-network-aware feature engineering;
    \item graph-based representations for delay propagation;
    \item improved objective functions and robust evaluation metrics beyond MAPE;
    \item scaling train coverage and extending the collection horizon.
\end{enumerate}

A particularly promising direction is graph-embedding-based station-delay prediction, as reported in recent literature \cite{chowdhury2025rstgcn}. This aligns with our observation that delay behavior is strongly segment-dependent and that the alpha indicator already exposes persistent structure which network-aware models should be able to exploit.
